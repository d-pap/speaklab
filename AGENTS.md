# SpeakLab development

If `.local/AGENTS.local.md` exists, read it first: it holds gitignored, machine-specific notes for a particular deployment and overrides nothing below.

## Project layout and checks

- Python package is installed editable from `backend`. Read `README.md` for the product workflow and `docs/deployment.md` for the optional Windows/WSL host setup.
- Run `.venv/bin/python -m pytest backend/tests -q`, `.venv/bin/ruff check backend`, and `npm --prefix frontend run build` from the root.
- Browser tests use dedicated ports 8766/5174 and `data/e2e`, which `frontend/e2e/reset-data.mjs` empties at the start of every Playwright run. Never aim them at normal practice data.
- The real-inference harness `scripts/smoke-inference.py` accepts two audio files and a report path. It creates a temporary database and uses actual loopback models. Its synthetic results are not user practice history.
- Never commit machine-specific values (hostnames, IP addresses, usernames, absolute home paths, tailnet names). Read them from environment variables or `.local/`, which is gitignored.

## Deployment

- A deployed host runs a dedicated WSL distro `SpeakLab`: source `/opt/speaklab`, practice data `/var/lib/speaklab`, config `/opt/speaklab/.env`. Keep secrets, recordings, `.venv`, `node_modules`, `.local`, and local data out of source transfer archives.
- Leave other WSL distros (for example Docker Desktop's) intact. Never use `wsl --shutdown` as a routine SpeakLab operation; use `wsl --terminate SpeakLab` only for an intentional recovery test.
- `wsl -d SpeakLab -u speaklab --cd /opt/speaklab --exec /opt/speaklab/.venv/bin/python ...` runs the app's Python commands. `runuser` is not on WSL's direct `--exec` PATH.
- Systemd starts the app, Ollama, and Whisper; a Windows startup task holds the distro open. The app serves the built frontend when `SPEAKLAB_SERVE_FRONTEND=true`. Rebuild on source changes and transfer `frontend/dist`; no Node process is needed on the server.
- Keep app and model listeners on loopback. Local development uses 5173; client tunnel port 4173 is reserved for a remote host.
- `scripts/connect-pc.command` wraps the standard-library `pc_connection.py` supervisor. It reads `SPEAKLAB_PC_*` settings from the environment or `.local/pc.env`, retries dropped SSH, pins the host key from `.local/ssh_known_hosts`, and uses an exclusive lock to prevent duplicate tunnels. Host-key/authentication failures stop for inspection. `--install` manages the macOS launch agent `dev.speaklab.pc-tunnel`; `--status`, `--stop`, `--uninstall` manage it. Tests: `/usr/bin/python3 -m unittest discover -s scripts/tests -v` (explicit SSH process doubles, no models).
- Optional private HTTPS uses Tailscale Serve (port 443 → app 8765, 8443 → Open WebUI 3000). Never use Funnel. `security.py` preserves exact origin/host and client-header checks; extra HTTPS origins come from the validated `SPEAKLAB_BROWSER_ORIGINS` JSON array, with no wildcard allowances. Keep `/opt/speaklab/.env` owned by `speaklab:speaklab`, mode 600.
- Optional Open WebUI is isolated under `/opt/open-webui`, data `/var/lib/open-webui`, systemd `open-webui`, config `/etc/open-webui.env`. It uses the existing Ollama with Tailscale trusted-header SSO and no password signup. Keep its listener on loopback; direct header-less sign-in must fail. Its chat data needs a separate backup from SpeakLab practice data.

## Inference constraints

- Everything is local: Ollama chat models and the whisper.cpp server on loopback, no hosted calls. The default model is Qwen3.5 9B Q4_K_M. Whisper small.en runs on CPU; the target GPU has 8 GB VRAM and holds one model and one request at a time.
- Five passes each have a model, `num_ctx` and `num_predict` (`llm.py`): `technical`, `communication`, `writer`, `chat`, `memory`. Defaults are the global model (Settings can change it, and each pass's model, context size and output limit separately under "Advanced: model per step"), 8192 context, 2048 output, and 4096 output for `writer`. A "prompt is too long" error points the learner to that setting. Every saved pass result records the model that produced it. Settings only offers installed local models and refuses changes while analysis or a coach reply is running.
- Keep dense pitch/loudness plot arrays out of model prompts. The stored arrays remain available to the UI. Models get a short plain-sentence voice summary instead.
- Supply the JSON schema in the prompt as well as the Ollama format field. Passes cite evidence by IDs from the input (transcript line IDs such as `L7`, concept IDs, reference IDs), never by copied text. Report all validation errors in one repair request; a second failure is reported on that pass.
- The model never writes the learner's words or timestamps. It emits markers: `[[L7]]` (time link) and `[[L7:"exact words"]]` (quote). `markers.py` resolves them from the stored lines: an unknown line ID is dropped, and a quote that is not an exact substring of its line falls back to the whole line. This covers the review message and every chat turn. The structured passes' written fields (concept notes, claims, corrections, observations, score reasons, key points, checklist items, what changed) are checked for clock times too, and a time goes back in the one repair request.
- Tests use explicit model doubles; only the optional smoke harness establishes real inference. A valid quote does not establish that its interpretation is correct.

## Feedback pipeline

- `speech.py` and `transcript.py` build timed transcript lines with stable IDs, filler marks and pauses between words. Context-dependent words ("you know", "I mean", "like", "so", "actually") are possible fillers, never definite ones. Edited transcripts get lines without times and no pause marks.
- `pipeline.py` runs one attempt at a time on a single worker. Phase 1: acoustics, transcription, lines, voice summary, then the `memory`, `technical` and `communication` passes. Phase 2: the `writer` passes (review structure, then the prose review message), which wait for the learner's optional "How did that go?" note or a 5 minute timeout. Each pass is saved as it finishes; a later failure keeps earlier results and a retry re-runs only the passes that are not done. A recording or an earlier pass result is never deleted by a failed step.
- `coach.py` holds the technical, communication, structure and message passes. The technical pass grades the learner against `topics.json` concept IDs and marks each point as in or not in the reference; corrections it marks wrong get a bounded second check and show as unverified if that fails. Omissions are never reported as errors. The communication pass returns sections by line ID (code turns them into time per section), strengths and problems with rewrites, knowledge-gap or communication-gap labels, and focus-area observations. The structure pass returns the scores, three key points and the checklist for next time. Only the writer passes get the previous attempt's review (`_previous_attempt` in `pipeline.py`): the structure pass receives it and, when the question type differs, both questions (`question_change`), and the message pass receives `question_change`, so the review says the question changed and reads score changes as indicative. The technical and communication passes see no earlier attempt.
- Before saving communication findings, proposed gaps and substantive criticism get a bounded check using the technical step, actual question, full transcript and topic references. A failed check downgrades proposed knowledge gaps to unclear. Structure receives the transcript and question; prose also receives the curated example, core and short voice summary. A single model across both steps is a second reading, not independent verification.
- Scores are out of 10 in 0.5 steps with a one-line reason, labelled as coaching estimates. Technical accuracy is unscored if the technical pass cites no concept evidence and proposes no correction. Core names: Overall, Clarity, Structure, Conciseness, Technical accuracy, Technical coverage, Handling uncertainty; focus-area scores may be added. Measurements are not judgements: do not turn pace, pitch or loudness into a good/bad score.
- A recording under 15 words gets no scores; the review says so, and if it is the latest attempt the learner may record it again the same day (it is replaced, keeping its number).
- `memory.py` keeps coach notes: plain text capped at 400 words, every version stored, folded in before each review from sessions and chats since the last update. The pass never removes a focus area. Learners can edit and restore versions in Settings.
- When the writer's prompt is over budget it shortens communication observations, drops senior points, cuts coach notes to their focus section, then drops concept notes; transcript lines, corrections and the review structure always stay.
- `chat.py` streams coach replies over server-sent events. Context order is fixed: system prompt, coach notes, transcript lines, review structure, both analyses, topic reference, recent turns. Older turns become a running summary (with the model that wrote it) when the budget is exceeded; notes, lines and the review stay in full. Chat is per attempt (`POST /api/sessions/{id}/chat` takes the attempt number); it is refused with a 409 while analysis runs; the browser gives a refused or unsent question back to the message box.
- Each topic has one practice thread: the earliest `sessions` row that has an attempt (`threads.py`). Schema v5 dropped the two-attempt limit, merged each topic's recorded sessions into one thread (attempts renumbered by date, messages and history following) and keeps sessions without recordings but never lists them. The `stage` and `completed_at` columns are unused; do not reintroduce stages. Threads are created lazily by the first `POST /api/topics/{topic_id}/attempts`; `GET /api/topics/{topic_id}/thread` creates nothing.
- Attempts are numbered without limit and each stores its own `prompt_kind`, style and duration (older attempts fall back to their session's). `threads.recording_state` decides what a recording may do: a new attempt opens from the next calendar day after the latest one (`threads.today()` is the seam for tests; a too-early upload is refused with a 409), and a too-short latest attempt that is not processing is replaced under its own number, even the same day. Each attempt keeps its own transcript, analysis, note and chat; coach notes carry memory across attempts.
- After each attempt's review is written, `pipeline.after_review_written` reschedules the topic's spaced review once, for the latest attempt only, from its technical results through `progress.mastery()` and `derived_recall()`. Retries, transcript edits and re-reviews do not schedule again.
- Endpoints: `GET /api/topics/{id}/thread`, `POST /api/topics/{id}/attempts`, `GET /api/history` (one row per practised topic), `GET /api/practice/ready` (practised topics with a new attempt open, due reviews first). The session-based start, stage, `attempt2` and completion routes are gone; `GET /api/sessions/{id}` remains so old `#/session/<id>` links can redirect to the topic page.
- `POST /api/attempts/{id}/rereview` runs the current pipeline again on a saved attempt, legacy ones included, archiving the earlier snapshot in `analysis_history`. Earlier sessions without the new analysis show their old assessment summary.
- Every catalog topic needs background, a bridge for each concept, practice context and curated sources; the reference grounds the passes and the chat.
- Schema v6 adds `messages.generation_context` and `response_feedback`. New written reviews and chat replies retain exact prose requests/options/raw outputs plus source transcript/analysis; keep this private context out of ordinary message API responses. Feedback snapshots are immutable after the first vote and survive message deletion via `ON DELETE SET NULL`; changing/removing a vote never calls models or updates coach notes/weights. Older responses explicitly lack generation context. `PUT /api/messages/{id}/feedback` saves or clears (`rating: null`); `GET /api/feedback/export` downloads uncurated local evidence. See `docs/coaching-feedback.md` for curation, reference provenance and train/evaluation separation.

## Interface

- `App.tsx` owns hash navigation (`#/today`, `#/topic/<id>`, `#/topic/<id>/new`, history, settings), the topic library and History by topic: one row per practised topic with attempt count, last attempt date and whether a new attempt is open. A `#/session/<id>` link looks up the session's topic and redirects to its topic page. The "Include practised" pill adds practised topics to suggestions and browsing; choosing a practised topic opens its topic page, never a new attempt 1. `Today.tsx` is the practice home: "Pick up where you left off" (most recently active topic), "Ready for another attempt" (from `/api/practice/ready`, due reviews first) and "Suggested topics" (never-recorded topics only, unless practised ones are included). Shared visual tokens in `styles.css` are neutral grays in both themes until a palette is chosen.
- `ReviewPage.tsx` is two columns on desktop. The left has Transcript, Review and Measurements tabs; the right has the optional note box and `CoachChat.tsx`. `TranscriptTab.tsx` shows continuous text with inline filler and pause marks and a stats line; `ReviewTab.tsx` shows scores, key points with time links and the checklist for next time; Measurements holds the acoustic and vocal displays. On a phone the chat is the main view and a button opens the transcript and review as a sheet. A time link in any coach message selects the transcript and highlights the line. Coach messages render a small, safe Markdown subset (headings, bold, bullet and numbered lists) as React nodes; model text is never inserted as HTML.
- `TopicPage.tsx` shows a row of attempt pills (latest selected) over the review page of the selected attempt; any attempt and its chat can be reopened. "New attempt" is enabled when `recording.can_record`, otherwise it reads "Next attempt opens tomorrow". `NewAttempt.tsx` is the clean recording screen, also used for a topic's first attempt: it shows only the topic, the question and the latest "For next time" checklist, with a "Try a different angle" question-type select defaulting to the previous attempt's type ("Question type" on the first attempt) and Cancel back to the topic page. Keep past reviews, chat and references out of it.
- The conversation offers a concept lesson and a delivery rehearsal through ordinary attempt chat. The optional rehearsal recorder uses the same browser capture/playback component as formal attempts, with no upload or scheduling. Only recorded threads expose the curated example and sources. Chat retains the core teaching reference until after analyses and review prose have been shortened.
- Settings holds the model picker (global and per-pass) and `CoachNotes.tsx`.
- `CoachControls.tsx` exposes the same app-wide model selection beside the coach conversation; it does not silently replace custom per-pass models on load. Regenerate review uses the full `/rereview` pipeline, archives the earlier prose/analysis, and retains chat, rated evidence and scheduling. `Rereview` shows archived prose with markers resolved against archived lines. Current messages label their producing model. Chat admission reserves `tutor_lock` under `mutation_lock`; regeneration refuses active replies before archiving anything.
- Frontend-only server updates need no service restart: back up the previous frontend, transfer new hashed assets first, then replace `frontend/dist/index.html` atomically. Keep old hashed assets available for already-open tabs. Do not overwrite the server's `.env` or practice data.
- `VocalVariation.tsx` presents one foundation at a time using stored metrics; `vocalMetrics.ts` derives comparable full-window ranges without rewriting attempts. Rate uses 30-second transcript windows; pitch/loudness use full 15-second `delivery_windows`. Never label low spread as quietness, monotone delivery or failure. Playback markers wait for audio metadata; keep the range-aware audio fixture in the browser tests.
